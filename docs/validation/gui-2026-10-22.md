# Capture GUI 原生流程验证

日期：2026-10-22。范围：Capture GUI 会话、原生 DRC 执行、PDF 导出。没有启动 Allegro/PCB Editor，也没有安装插件或修改 Cadence 安装文件。

## 实际执行与保护范围

通过 computer-use 的 Windows 窗口 API 启动 Capture CIS 24.1。Capture 自动恢复了已有工程；后续测试明确打开 `.local/gui-validation/gui_fulladd.dsn`，这是安装内 FULLADD 示例的新副本。每次 Tcl 探测/导出校验 `GetActivePMDesign` 返回的完整路径。已有工程与安装示例的 DSN 指纹在测试前后保持一致。

外置脚本从工作仓库临时 source，没有写 capinit 或自动加载目录，没有启动 TCP 服务。Capture 自有 Dbo session 没有被删除。

## DRC 诊断

- 6 条 ORCAP-1604：重复物理脚号关联多个网络，报告涉及重复 HALFADD 层次中的 package/pin 关系。
- 13 条 ORCAP-36002：缺少 PCB Footprint 属性。
- 原生报告将本次 19 条错误列于 physical 检查段；不能把“电气段未出现 error 行”解释为整电路电气正确。
- 没有修复样例电路，也未把该样例作为应当零 DRC 的标准 fixture。

`cadence_mcp.drc.parse_drc` 与 `tools/summarize_drc.py` 新增只读摘要能力，识别有/无编号的诊断、严重程度、错误码及检查段。解析器始终将 `executionVerified=false`：解析文件本身不能证明命令运行完成或使用了正确工程。真正的运行依据还包括活动路径、原生 Run 操作、文件新生成及当前时间。

## PDF 路径与依赖

本机现有 OrCADPS_24.1 PostScript 队列，以及 Capture 已配置的可用 64 位 Ghostscript 转换器。没有安装或下载新的打印依赖。转换器绝对路径保留在忽略的本机探测文件中，不写死在项目实现里。

`tools/gui_export_pdf.tcl` 使用经过本机源码核对的 `::capPdfUtil::printPdfEx`，校验活动设计和输出文件，拒绝覆盖旧 PDF，临时设置打印模式/方向等，并在 finally 中恢复对应配置。保留 PS/mark 文件作为诊断材料，关闭自动外部查看器。

本次 PDF 使用实例/定义模式，整设计预期为 2 页，不是对所有 occurrence 各打印一份。仅校验 DSN 路径还不够：GUI 当前选择影响页范围，未来 MCP export 契约必须同时验证 scope 与页清单。脚本当前仍是有人监督的手动验证工具，不是可直接开放给 AI 的自动 export 工具。

PDF 原生字体的文本提取呈 glyph 名称，不能可靠进行全文检索；实际渲染可读。没有把文本提取当作图面或网络验证。没有宣称 bookmark、中文字体、多种纸型和复杂多页工程均兼容。

## 更正：PDF 默认采用 Print（后续同日验证）

前述 `gui-design.pdf` 是历史 Export 输出，其“最终两页”仅代表当时图面验证，不满足现行文字交付要求。`printPdfEx` 属于 Export → PS → Ghostscript 流程，不能按名字解释为 File → Print。

已在同一测试副本的设计根节点实际执行 File → Print → Microsoft Print to PDF：A4 横向、Scale to paper size、600 dpi、Inst. Mode，输出新的 `gui-print.pdf`。两页 FULLADD/HALFADD 均独立渲染并检查，文字与连线可读、无截断。pypdf 6.10.0 提取出正常网络名和位号，PDFium 对 CARRY_OUT（第一页）和 X_BAR（第二页）执行文字查找并能提取命中范围。旧 Export 输出不能提取这些预期文字。

这验证了样例的原生文字层提取和查找，不等于已经在目标阅读器实际操作全局查找/剪贴板，也不涵盖中文、特殊字体和复杂工程。GUI Print 尚未接入 MCP。PDF 的网络名文本不等于可供仿真的网表。

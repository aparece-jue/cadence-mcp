# 研发、验收与Git同步

用户2026-10-25授权后续研发成果持续同步Git。开发与试用并行：开发成果按完成批次提交并推送`develop`，`main`及已发布tag作为发布基线；新版本使用新tag，不覆盖用户正在测试的alpha.1。用户测试固定wheel环境，开发源码与其隔离。

## 一个研发批次应留下什么

1. 原子目标及官方依据：在既有34项清单中明确对应ID、实现方法、独立预期和验收条件。
2. 源码与契约：同时维护Python/Tcl、配置示例、安装/使用文档及实际tools/list契约。
3. 验收与问题：区分主机测试、真实Dbo/CLI/MCP、尚未验证、失败与依赖。异常保留原预期、输出和摘要，按原计划后移；不得放宽门禁自证完成。
4. 管理记录：同步cadence-acceptance.json、CURRENT-STATE.md和批次记录，说明已完成、未完成与下一步。
5. 生成进度：运行`python tools/update_progress.py`，再用`--check`确认进度页、SVG、JSON、参考索引和README一致。
6. 检查与同步：运行与本批改动相称的检查，审查可公开文件后提交并推送develop。小步骤不必每次推送；按有明确成果、证据或失败定位的批次同步，避免不完整状态被描述为可用版本。

## 如何看完成度

[进度页](PROGRESS.md)的主指标为“完整验收通过数 / 原34个必需子目标”。只计passed，baseline_passed和implemented_partial均不计。各项工作量不同，百分比不是代码量或剩余工时估计；工具数和自动测试结果单独报告。发现新问题可能导致状态回退，必须如实记录；不能删除困难项或缩减分母提高百分比。

## 哪些资料上传

上传原创源码、架构/计划/进度、问题和验收摘要、使用说明、可公开最小复现、参考文档索引和文件指纹。官方手册/安装文件按本机路径定位，见[参考索引](references/INDEX.md)，不将受限全文搬入公共仓库。真实设计、外部模型、许可证和认证资料、私有原生输出继续保留本地；其脱敏结论与摘要可公开。

## 用户反馈进入研发

反馈注明固定版本、目标操作、工具/步骤、错误码和planId/jobId；在许可允许的最小样例上复现，再加入现有子目标的问题列表。先处理影响用户实际试用的回归与阻断，再按依赖推进原计划。修复后重测受影响能力并记录版本，不能用其他成功测试替代原失败条件。
